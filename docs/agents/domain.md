# Доменные доки

Как инженерные скиллы должны использовать доменную документацию этого репозитория при исследовании кода.

## Перед исследованием прочитай

- **`GLOSSARY.md`** в корне репозитория.
- **`docs/adr/`**: ADR, относящиеся к области, в которой собираешься работать.

Если этих файлов нет — **продолжай молча**. Не отмечай их отсутствие и не предлагай создать заранее. Скилл `/domain-modeling` (через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно появляются.

## Раскладка

Single-context:

```text
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
├── apps/
└── packages/
```

## Используй словарь глоссария

Когда в выводе называешь доменное понятие (в заголовке issue, предложении рефакторинга, гипотезе, имени теста), используй термин из `GLOSSARY.md`. Не уходи в синонимы, которых глоссарий избегает.

Если нужного понятия в глоссарии нет — это сигнал: либо ты придумываешь язык, которого в проекте нет (пересмотри), либо есть реальный пробел (отметь для `/domain-modeling`).

## Отмечай конфликты с ADR

Если вывод противоречит существующему ADR, явно покажи это, а не переопределяй молча:

> _Противоречит ADR-0007 (event-sourced orders), но стоит переоткрыть, потому что…_
